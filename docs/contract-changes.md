# Предложения по изменению контрактов

Агенты **не меняют** `src/lib/contracts.ts` и формат `data/kb/` сами. Предложение пишется сюда, тимлид принимает или отклоняет.

```
## ГГГГ-ММ-ДД [роль] — краткое название
**Что изменить:** поле/схема
**Зачем:** ...
**Кого затрагивает:** backend / frontend / amocrm / eval
**Статус:** предложено | принято | отклонено (причина)
```

---

## 2026-09-30 [backend-dev] — модель, которая реально ответила, в meta
**Что изменить:** `AssistMetaSchema` + `model: z.string()` (например `"nvidia/nemotron-3-super-120b-a12b:free"`).
**Зачем:** с `LLM_FALLBACK_MODELS` OpenRouter может ответить не той моделью, что указана в `LLM_MODEL`. Для eval и разбора ответов важно знать, какая модель дала конкретный ответ. Сейчас это видно только в `logs/usage.jsonl`.
**Кого затрагивает:** backend (одна строка), eval (группировка метрик), frontend (можно показать в UI).
**Статус:** предложено

## 2026-09-30 [backend-dev] — buildUserMessage и RetrievedChunk.product_id
**Что изменить:** в `src/lib/prompts/system.ts` экспортировать `buildUserMessage(req: AssistRequest): string` (уже в планах prompt-engineer). В `RetrievedChunk` добавить необязательное `product_id?: string`.
**Зачем:** сейчас `assist.ts` использует локальный адаптер `buildUserMessageLocal`, при слиянии его нужно заменить. `product_id` позволит промпту связать найденные чанки с `trigger_product_ids` матрицы допродаж.
**Кого затрагивает:** prompt-engineer, backend.
**Статус:** предложено

## 2026-09-30 [kb-builder] — фиксированный словарь `exclude_if`
**Что изменить:** в `data/kb/README.md` описать `exclude_if` как enum, а не свободные строки: `complaint | negative_sentiment | contraindications | needs_human | minor`. Сейчас в README есть только пример из трёх значений и «и т.п.».
**Зачем:** LLM-слой и eval должны одинаково понимать, когда правило отключается. `needs_human` отключает допродажу, если обращение уходит менеджеру. `minor` отключает её, если клиент несовершеннолетний: Минеральный комплекс по инструкции рекомендован с 18 лет. Оба значения уже используются в `upsell-matrix.json`.
**Кого затрагивает:** backend (фильтрация правил), prompt (описание в промпте), eval
**Статус:** предложено

## 2026-09-30 [kb-builder] — цена с промокодом в `products.json`
**Что изменить:** добавить в формат товара необязательные поля `price_promo_rub?: number | null` и `price_checked_at?: string` (ISO-дата).
**Зачем:** на сайте у каждого товара две цены: без промокода и с промокодом, выдаваемым перед оформлением. Сейчас в `price_rub` лежит цена без промокода, а цена с промокодом записана строкой в `todo` и оттуда же попадает в чанк. Это хрупко, и UI её не видит.
**Кого затрагивает:** frontend (карточка товара), backend (если цена подмешивается в промпт), kb-builder
**Статус:** предложено

## 2026-09-30 [kb-builder] — наборы как отдельный вид товара
**Что изменить:** добавить в формат товара `kind?: "product" | "set"` и `includes?: string[]` (id товаров, входящих в набор).
**Зачем:** наборы O-complex (например «Детокс» = 2 × СТАНДАРТ + Минеральный комплекс) лежат в `products.json` вместе с обычными товарами. Правила «замените отдельные товары набором» сейчас держатся только на тексте `why`. С полем `includes` backend сможет проверять, что клиент уже собирает состав набора.
**Кого затрагивает:** backend, kb-builder
**Статус:** предложено

## 2026-09-30 [kb-builder] — уточнить комментарий к `UpsellSchema.product_id`
**Что изменить:** в `src/lib/contracts.ts` комментарий «только id из data/kb/upsell-matrix.json» заменить на «`offer_product_id` одного из правил upsell-matrix.json (это id из products.json)». По желанию добавить `rule_id?: string` (id правила, например `upsell-006`).
**Зачем:** в матрице два вида id: id правила (`upsell-001`) и id товара (`offer_product_id`). Из текущего комментария неясно, какой из них ждёт схема. С `rule_id` eval сможет проверять, что допродажа взята из разрешённого правила.
**Кого затрагивает:** backend, prompt, eval, frontend
**Статус:** предложено

## 2026-09-30 [kb-builder] — перенести сборку чанков в scripts/
**Что изменить:** генератор `data/kb/tools/build-chunks.mjs` перенести в `scripts/build-chunks.ts` и добавить npm-скрипт `build-chunks`, который запускается перед `build-index`.
**Зачем:** `chunks.json` производный от `products.json`, `faq.md` и `policies.md`. Генератор положен в `data/kb/tools/` только потому, что `scripts/` не в зоне kb-builder.
**Кого затрагивает:** backend (build-index)
**Статус:** предложено
