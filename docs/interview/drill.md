# Флеш-карты: 10 самых вероятных вопросов

Как тренироваться: закройте ответ, скажите вслух за 45–60 секунд, потом сверьтесь. Ответ засчитан, если в нём есть все три части: **суть, пример из проекта, компромисс**. Полные версии — в [`questions.md`](questions.md), слабые места — в [`gaps.md`](gaps.md).

### 1. Расскажите, как устроен ваш ассистент.
<details><summary>Ответ</summary>

- **Суть:** ядро `assist()`: поиск по базе (локальные эмбеддинги e5-small, cosine, top-5) → промпт с фрагментами, политиками, матрицей допродаж → модель через OpenRouter возвращает JSON по zod-схеме → код проверяет допродажу, `needs_human`, язык, источники. Два входа: демо-UI и вебхук amoCRM.
- **Пример:** один контракт `src/lib/contracts.ts` для UI, API, примечания в amoCRM и eval.
- **Компромисс:** всё в одном Next-приложении, без БД и очереди. Для продакшена ядро — отдельный сервис с очередью.
</details>

### 2. Почему не LangChain?
<details><summary>Ответ</summary>

- **Суть:** один вызов модели и поиск по 49 фрагментам. AI SDK и своих 120 строк поиска достаточно, и я точно контролирую число запросов (`maxRetries: 0` при лимите 50 в день).
- **Пример:** `src/lib/llm.ts`, `src/lib/retrieval.ts`.
- **Компромисс:** для агентов с инструментами и многошаговых цепочек фреймворк окупится. В продакшене с ним не работал, понимаю его модель.
</details>

### 3. Зачем RAG при такой маленькой базе?
<details><summary>Ответ</summary>

- **Суть:** честно, база влезла бы в контекст. Поиск даёт меньше лишних фактов, проверяемые `sources` и готовность к росту базы.
- **Пример:** политики и матрица идут в промпт всегда, поиск — только по товарам и FAQ.
- **Компромисс:** вход ~11–12 тыс. токенов из-за полной матрицы; поиск промахнулся на акциях и лекарствах; пороги подбирались на 6 dev-фрагментах.
</details>

### 4. Как вы не даёте модели обещать лечебный эффект и придумывать допродажи?
<details><summary>Ответ</summary>

- **Суть:** модель предлагает, код проверяет. Допродажа — только `rule_id` из матрицы, код проверяет правило целиком, тексты берутся из матрицы. Темы здоровья и жалобы — `needs_human` кодом, даже если модель этого не поставила.
- **Пример:** модель выдумала товар и «улучшит пищеварение»; на «я беременна» поставила `needs_human: false`. Обе ошибки закрыты кодом в `postProcess`.
- **Компромисс:** регулярки видят только последнее сообщение и не видят перефразировок («я в положении»). Ответ — черновик, отправляет человек.
</details>

### 5. Как вы проверяете качество?
<details><summary>Ответ</summary>

- **Суть:** 20 кейсов по рискам домена, автопроверки, LLM-судья по рубрике, ручное чтение, сравнение версий через `--baseline`.
- **Пример:** v1.1: все проверки 72%, `needs_human` 92%, язык 89%. Ручное чтение нашло утечку учебных фактов из few-shot в 5 из 18 ответов: автопроверки её не видели, судья поймал 3 из 5.
- **Компромисс:** выборка маленькая; полные прогоны только v1.1 и v1.2, v1.3–v1.5 — точечные по 2–7 ответов. Это регрессия, а не статистика.
</details>

### 6. Как защищаетесь от prompt injection?
<details><summary>Ответ</summary>

- **Суть:** слои. Данные клиента в user-сообщении и тегах; `escapeData()` не даёт закрыть тег; few-shot с инъекцией; опасные решения (допродажа, тексты подсказки) не у модели; у модели нет инструментов; ответ — черновик.
- **Пример:** три eval-кейса (скидка 90%, раскрытие промпта с `</client_message>`, «правило» в истории): успешных инъекций не было.
- **Компромисс:** защита промптом вероятностная. С инструментами нужны права в коде и подтверждение человеком.
</details>

### 7. Как работает интеграция с amoCRM и что с идемпотентностью?
<details><summary>Ответ</summary>

- **Суть:** вебхук `add_message` → проверка секрета и схемы → 200 сразу (amoCRM ждёт 2 с) → в `after()` контекст сделки через REST v4 → `assist()` → примечание. Повтор отсекается по id сообщения.
- **Пример:** REST не отдаёт текст чатов, поэтому переписка копится из вебхуков.
- **Компромисс:** live не проверен на реальном аккаунте; дедупликация в памяти; id помечается до вызова модели, и при ошибке подсказка теряется. В продакшене: очередь, таблица обработанных событий, ретраи воркером.
</details>

### 8. Сколько это стоит и как контролировать расход токенов?
<details><summary>Ответ</summary>

- **Суть:** измерил: вход ~11–12 тыс. токенов, выход ~1 тыс., ~92% стоимости — вход. Платный аналог ≈ $1,3–1,5 на 1000 обращений.
- **Пример:** `logs/usage.jsonl` на каждый вызов (модель, токены, латентность, попытки); бюджет запросов в eval; сетевые ретраи выключены.
- **Компромисс:** главный рычаг — передавать не всю матрицу, а только подходящие правила, и кэш префикса. Каждое сокращение проверять eval.
</details>

### 9. Как вы контролируете код от ИИ? Пример ошибки ИИ.
<details><summary>Ответ</summary>

- **Суть:** контракты до кода, зоны файлов, «готово» = typecheck + lint + запуск, журнал ошибок ИИ, внешние факты — по официальной документации.
- **Пример:** ИИ рекомендовал закрытый GitHub Models по обзорам; написал «проверено» про модель, которая ни разу не ответила; использовал устаревший `generateObject`; снёс папку `.claude/` вместо одного файла. Всё в `docs/ai-log.md`.
- **Компромисс:** постоянных юнит-тестов нет, офлайн-проверки были разовыми скриптами. Первое, что добавлю, — Vitest и CI.
</details>

### 10. Персональные данные и выбор модели в РФ?
<details><summary>Ответ</summary>

- **Суть:** сейчас имя и переписка уходят в OpenRouter за рубеж. Для демо допустимо, для продакшена нет: уведомление РКН до трансграничной передачи (ст. 12 152-ФЗ), здоровье — специальная категория (ст. 10).
- **Пример:** эмбеддинги уже локальные; провайдер модели меняется одной записью в `PROVIDERS`. GigaChat рассматривался, но нет провайдера для AI SDK.
- **Компромисс:** модель в российском контуре или на своём сервере, маскирование перед отправкой, логи без текстов, решение с юристом. Выбор — по нашему eval, а не по рейтингам.
</details>
