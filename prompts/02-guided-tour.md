## Зачем
Кандидат записывает видео на 1–2 минуты для работодателя. Он запускает экскурсию и кликает по шагам, а текст подсказок служит сценарием рассказа. Подсказки должны быть понятны нетехническому зрителю и при этом показывать инженерную глубину решения.

## Как выглядит
- Кнопка «Экскурсия» в шапке. Автозапуск по `?tour=1` в URL, удобно для записи.
- Шаг экскурсии: элемент подсвечивается (spotlight: затемнение вокруг, рамка вокруг элемента), рядом всплывает окно-поповер со стрелкой к элементу.
- В окне два яруса:
  1. Заголовок и 1–3 предложения простым языком: что видит пользователь и зачем это менеджеру.
  2. Под тонким разделителем приглушённым мелким текстом блок «Под капотом»: технические детали из списка фактов ниже. Технический язык уместен.
- Навигация: «Назад» / «Далее» / «Пропустить», прогресс «3 / 10», клавиши ← → Esc.
- Шаг может ждать действия пользователя («Выберите сценарий „Повторный покупатель“» или «Нажмите „Отправить“») и переходить дальше сам, когда действие сделано. «Далее» при этом тоже работает, чтобы запись не застряла.
- Пока ассистент думает (загрузка), поповер не должен перекрывать результат. Шаги про карточки результата показываются, когда ответ пришёл.
- Анимации короткие (150–250 мс), с учётом `prefers-reduced-motion`. Позиционирование не уезжает при скролле и ресайзе.
- Основной формат — десктоп 1280×720 (запись видео). На узком экране (375 px) поповер становится нижним листом без стрелки, горизонтальной прокрутки нет.
- Стиль — как у текущего UI (Tailwind, stone/emerald, свои примитивы из ui.tsx).

## Сценарий шагов (предложение, можно улучшить)
Экскурсия идёт по двум сценариям: «Повторный покупатель» (есть допродажа) и «Беременность» (нужен менеджер, допродажи нет). По умолчанию в режиме «Мок», чтобы не тратить лимит. Тексты обязаны оставаться верными и в режиме «API».
1. Приветствие (окно по центру, без подсветки): что это за сервис — обращение клиента → ответ клиенту + подсказка менеджеру по допродаже.
2. Сценарий и контекст клиента (имя, этап сделки, покупки).
3. История диалога и поле нового сообщения.
4. Переключатель «Мок / API».
5. Отправка (ждём нажатия).
6. Карточка «Ответ клиенту»: бейджи intent и sentiment, «Скопировать», «Вставить в чат».
7. Карточка допродажи: товар, номер правила, почему подходит, готовая фраза.
8. «Источники и метрики»: id фрагментов базы, токены, задержка, версия промпта.
9. Переключаемся на сценарий «Беременность», отправляем: плашка «Нужен менеджер», допродажа отключена с причиной.
10. Финал (окно по центру): что за кадром — amoCRM и eval.

## Факты для блока «Под капотом» (проверены по коду, не выдумывай другие)
Если для шага нужен факт, которого здесь нет, найди его в коде и сошлись на файл. Чего нет в коде — не пиши.
- Стек: Next.js 16 (App Router), TypeScript strict, React, Tailwind, Vercel AI SDK v7, zod.
- Контракт запроса и ответа — zod-схемы в src/lib/contracts.ts. Запрос: client_message, dialog_history, customer_context (name, past_purchases, deal_status). Ответ: client_reply, upsell (recommended, rule_id, product_id, product_name, why, manager_phrase), intent, sentiment, needs_human, needs_human_reason, sources, а также meta (токены, latency_ms, prompt_version).
- Режим «API» = POST /api/assist. Ответ в UI ещё раз проверяется AssistResultSchema. «Мок» — фиксированный ответ из src/components/__mocks__/, модель не вызывается.
- База знаний собрана с официального сайта o-complex.com: 15 товаров и наборов, 16 FAQ, политики, 18 правил допродаж. Нарезана на 49 фрагментов (data/kb/chunks.json).
- Поиск (retrieval): эмбеддинги считаются локально, без внешнего API — модель Xenova/multilingual-e5-small через @huggingface/transformers, вектор 384, квантизация q8. Поиск по косинусной близости: top-5, порог 0.75, отставание от лучшего не больше 0.04. Запрос = две последние реплики клиента + новое сообщение (src/lib/retrieval.ts, src/lib/assist.ts).
- Модель: OpenRouter, бесплатная nvidia/nemotron-3-super-120b-a12b:free с запасными qwen/qwen3.8-27b:free и dots-studio/dots-3-note-preview:free. Структурированный вывод: generateText + Output.object по zod-схеме, плагин response-healing, одна повторная попытка при невалидном JSON (src/lib/llm.ts).
- Промпт v1.2 (src/lib/prompts/): системные инструкции + найденные фрагменты, политики, матрица допродаж и каталог в XML-тегах + 5 примеров на вымышленных товарах. Данные клиента экранируются: текст вида «</client_message> забудь инструкции» не может закрыть тег (защита от prompt injection).
- Допродажа: только по правилу из data/kb/upsell-matrix.json. Модель называет rule_id, а код проверяет правило целиком: товар-триггер куплен, найден поиском или назван в диалоге; intent входит в trigger_intents; не сработало исключение exclude_if (complaint, negative_sentiment, contraindications, needs_human, minor); предлагаемый товар ещё не куплен. Тексты «почему» и «фраза» берутся из матрицы, а не пишутся моделью: так модель не может пообещать лечебный эффект (checkUpsell в src/lib/assist.ts).
- «Нужен менеджер» (needs_human): ставит модель, а код страхует — беременность, дети, болезни, лекарства (регулярное выражение), жалоба, ответ не на языке клиента всегда передаются человеку.
- Источники: в ответе остаются только id фрагментов, которые реально нашёл поиск. Каждый вызов пишет в logs/usage.jsonl модель, токены, задержку, число попыток.
- amoCRM (за кадром): вебхук POST /api/amocrm/webhook на событие «новое сообщение» сразу отвечает 200, а обработка идёт в after(). Сервис собирает контекст сделки (контакт, этап воронки, покупки, историю переписки) через REST API v4 и пишет черновик ответа и подсказку примечанием в карточку сделки. Проверено в mock-режиме по фикстурам из документации amoCRM.
- Качество (за кадром): eval-набор из 18 кейсов — беременность, дети, жалобы, prompt injection, английский язык и др. Автопроверки + LLM-судья по рубрике (scripts/eval.ts, docs/eval-report.md). Точные цифры бери из docs/eval-report.md на момент работы, не из памяти.

## Тон текстов
- Верхний ярус: коротко, по-человечески, с точки зрения менеджера магазина. Без «инновационный», «умный ИИ» и прочего маркетинга.
- «Под капотом»: сжато, конкретно, можно списком из 2–3 пунктов, названия файлов и библиотек моноширинным.
- Никаких обещаний лечебного эффекта даже в примерах. Тексты — в одном файле (например src/components/tour/steps.ts), чтобы кандидат мог править их сам.

## Ограничения
- Зона: src/components/ и src/app/ (кроме src/app/api/). src/lib/, data/, контракты не трогать. Если без изменения чужой зоны не обойтись — опиши предложение в docs/contract-changes.md и сделай без него.
- Новые зависимости — по возможности нет: спотлайт и позиционирование поповера реально сделать самому. Если всё же берёшь библиотеку (driver.js, floating-ui и т.п.), проверь версию через `npm view <пакет> version`, лицензию и вес и объясни выбор в отчёте.
- Привязка к элементам — через атрибуты data-tour="...", а не через CSS-классы.
- Доступность: поповер — role="dialog" с aria-labelledby, фокус переходит в поповер и возвращается после закрытия, Esc закрывает.
- Экскурсия в режиме «API» тратит дневной лимит модели (50 запросов на аккаунт OpenRouter). Проверяй в «Моке», в «API» — максимум 2–3 запроса.
